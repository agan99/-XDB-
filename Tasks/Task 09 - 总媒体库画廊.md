# Task 09 - 总媒体库画廊

> **阶段：Requirement 重写完成，等待 Plan Review。**
>
> 本文件只定义“必须实现什么”和“不能越过什么”。它不是 Approved Plan。没有用户批准的 Plan Review，不得修改插件、XDB 或媒体笔记。

## 1. Goal

建立一个总媒体集合画廊，在同一个结果区域浏览媒体记录，并通过顶部导航筛选媒体类型、状态、收藏和搜索结果。

总集合负责全局浏览；动画、游戏等类型库继续负责各自的专属进度。总集合卡片默认只读，不复制类型库的进度操作。

## 2. Requirement

### 2.1 顶部导航

导航分组和顺序固定为：

```text
[★收藏] 🔍 搜索…… [全部][动画][游戏][剧集][电影][书籍][漫画]
| [全部][待定][进行中][已完成][暂缓]
| [个人评分][完成日期]
```

窄窗口允许换行，但不能改变组内顺序和组之间的语义。

### 2.2 收藏

- `★收藏` 是独立开关，只匹配笔记中的 `收藏 = true`。
- 收藏筛选与类型、状态和搜索条件使用 AND。
- 收藏筛选只改变结果，不修改 `收藏` 属性。

### 2.3 媒体类型

类型按钮顺序固定为：`全部、动画、游戏、剧集、电影、书籍、漫画`。

- 类型筛选可以多选，多个类型取 OR。
- `全部` 清空类型选择，表示显示当前集合支持的全部类型。
- 类型筛选与收藏、状态和搜索使用 AND。
- `作品大类` 缺失或不在当前集合允许值内的记录不应被错误归入某个类型。
- 当前已确认的类型卡片规则来自动画和游戏；剧集、电影、书籍、漫画的专属字段和状态显示词必须遵循《媒体库新媒体类型接入边界》，不能从动画或游戏自动推导。

### 2.4 状态

笔记保存中性状态：

```text
💭 未来也许
⏳ 待定
▶️ 进行中
✅ 已完成
```

状态按钮顺序固定为：`全部、待定、进行中、已完成、暂缓`。

- 状态筛选为单选；再次点击当前状态回到 `全部`。
- 筛选按钮使用中性词，不显示“想看 / 在看 / 想玩 / 在玩”。
- 状态筛选只改变结果，不修改笔记中的状态值。
- 卡片是否使用媒体类型专属状态词，按《媒体库集合卡片设计规范》和对应类型 Requirement 处理；未确认的类型使用中性状态词。

### 2.5 搜索

搜索范围只包括：

- `中文名`
- `原名`
- `tags`

规则：

- 包含匹配；英文字母忽略大小写；忽略首尾空格；
- 多个关键词按空格拆分，关键词之间使用 AND；
- 每个关键词可以命中上述三个字段中的任意一个；
- 不搜索 `description`、正文内容或未列入本 Requirement 的字段。

### 2.6 排序

顶部只提供两个排序入口：

```text
个人评分
完成日期
```

- 个人评分按数值排序，空值必须稳定地排在有值记录之后；`0` 是有效值。
- 完成日期按有效日期排序，空值必须稳定地排在有值记录之后。
- 排序只改变结果顺序，不写回笔记。
- 同值记录必须有稳定的次级顺序，不能因刷新随机跳动。
- 默认排序顺序、按钮方向和是否采用三态循环，属于 Plan Review 必须确认的实现决策；不得从旧 Task 09 直接继承“日期回落”或旧排序键。

### 2.7 结果和布局

- 结果区使用规则网格，不使用瀑布流。
- 卡片等高或通过明确的正文布局保持行列稳定。
- 卡片列数根据可用宽度变化，不能产生横向滚动条。
- 条件变化后重新计算完整结果，再渲染当前结果；不能只在已经渲染的卡片上筛选。
- 是否采用渐进加载、批次大小和触发方式在 Plan Review 中确认；如果采用，必须先完成筛选、搜索和排序，再分批生成 DOM。
- 没有结果时区分集合为空和当前条件无匹配。

### 2.8 空结果

必须区分：

1. 集合没有任何可展示记录；
2. 集合有记录，但当前条件没有匹配结果。

两种状态都要提供清晰文字。筛选无结果时提供清除条件入口；清除条件不应擅自修改媒体笔记。

## 3. 集合通用卡片

集合卡片使用一套通用结构，结构和信息流遵循《媒体库集合卡片设计规范》及《媒体库展示视觉效果管理规范》。

公共展示范围：

- 封面或明确的缺失封面占位；
- `作品大类` 类型角标；
- 状态角标；
- 已正式约定的日期角标；
- `个人评分`；
- `中文名 → 原名 → name` 标题回落；
- `收藏 = true` 时的收藏标记；
- 最多 5 个有效 `tags`。

集合通用卡不显示：

- 简介或简介悬浮层；
- 推荐语；
- 产地；
- 动画进度条、已观看集数和集数增减；
- 游戏累计游玩时间和平台编辑；
- 未经本 Task 明确授权的编辑控件。

集合卡片默认只读。卡片视觉尺寸、主题变量、角标可读性、hover/focus 和缺失字段降级遵循视觉管理规范，不在本 Task 中重复冻结具体 CSS 数值。

## 4. 数据和职责边界

- 总集合与类型库读取同一批媒体笔记，不复制、迁移或另存业务数据。
- `source`、全局 filter、View filter、字段 Renderer 和 Database View 的分工遵循《媒体库 XDB 架构与职责边界》。
- 画廊负责集合级筛选、搜索、排序、统计、布局和加载；卡片负责单条记录展示。
- 不在总画廊中复制动画或游戏卡片的业务逻辑。
- 展示模型是临时派生值，不自动写回 frontmatter。
- 状态、收藏、评分、进度和其它属性的写回遵循《媒体库交互与写回边界》；本 Task 不授权总集合写回。

## 5. Scope

本 Task 负责：

- 总集合画廊的需求定义；
- 顶部导航、筛选、搜索和排序交互；
- 集合结果、空状态、网格和加载行为；
- 一套只读通用集合卡片；
- 与现有动画、游戏类型库的职责隔离；
- 自动验证和真实 Obsidian/Components 人工验收设计。

## 6. Out of Scope

- 修改动画或游戏卡片的既有业务逻辑；
- 修改 `媒体库单个视图.xdb` 或其它现有 XDB，除非批准后的 Plan 明确列为 Target File；
- 创建或修改电影、剧集、书籍、漫画的类型专属字段、卡片或进度逻辑；
- 迁移、批量修复或覆盖媒体笔记；
- 外部来源抓取、数据接入和 frontmatter 更新策略；
- 总集合中的状态、收藏、评分、进度或其它业务写回；
- 从 `Reference/参考-设计规范.md` 继承简介、推荐语、产地或旧类名；
- 因视觉复用而复制动画集数操作或游戏游玩时长逻辑。

## 7. Target Files

Target Files 不在本 Task 中预先冻结。Plan Review 必须根据当前真实文件、XDB schema 和插件 API 确认：

- 总集合使用已有 XDB、独立 XDB 还是其它已支持的配置方式；
- 是否新建独立 `*.xdb.js` 插件；
- 是否需要新增测试文件；
- 哪些现有文件必须保持不变。

在 Target Files 获得批准前，不得创建不存在的“媒体库.xdb”、总集合插件或配套字段作为既定实现。

## 8. Acceptance Criteria

1. 顶部导航分组和顺序符合本 Task 规定。
2. 类型筛选支持多选，`全部` 能清空类型选择。
3. 状态筛选使用中性词、单选，重复点击能恢复全部。
4. 收藏、类型、状态和搜索组合使用 AND；多类型内部使用 OR。
5. 搜索只读取中文名、原名和 tags，并满足多关键词 AND。
6. 只提供个人评分和完成日期两个排序入口；空值不挤到有效值之前。
7. 条件变化重新计算完整结果，不依赖当前已渲染 DOM。
8. 集合卡片只展示公共集合信息，不展示简介、推荐语、产地或类型专属进度操作。
9. 集合卡片默认只读，没有未经授权的写回调用。
10. 缺失封面、标题、日期、评分、标签和类型信息时按规范降级，不保留无意义空壳。
11. 网格响应式变化不产生横向滚动条。
12. 区分集合为空和条件无匹配两种空状态。
13. 动画和游戏现有卡片、画廊和进度职责不因总集合需求被隐式改变。
14. 实施后通过对应的静态检查、自动测试、XDB/plugin validator 和真实 Obsidian/Components 人工验收。

## 9. Verification / Human Acceptance

### 9.1 Agent Verification

Plan Review 必须设计并覆盖：

- 类型多选、全部清除和状态单选；
- 收藏、搜索关键词、大小写、空格和字段范围；
- 个人评分、完成日期、空值和稳定次级排序；
- 六类类型的公共卡片降级；
- 无进度条、无简介入口、无未经授权写回；
- 结果重算、空状态和加载行为；
- 目标文件未误修改的静态检查。

### 9.2 Human Acceptance

在真实 Obsidian/Components 中确认：

- 顶部导航顺序和分组清楚；
- 动画、游戏记录能按条件展示；
- 类型多选、状态筛选、收藏、搜索和两个排序入口可理解且稳定；
- 卡片视觉符合视觉管理规范；
- 卡片不出现简介、推荐语、产地、进度条、游玩时长或集数操作；
- 窄窗口无横向滚动；
- 现有动画和游戏类型库仍保持原行为。

## 10. Plan Review 前置问题

Plan Review 必须先回答以下问题，不能直接从旧稿复制答案：

1. 总集合的真实 XDB 入口是什么，是否需要新建 .xdb 或 *.xdb.js；
2. 六类 作品大类 的入库边界如何表达，缺失值如何处理；
3. 完成日期的字段类型、有效值和排序方向如何确认；
4. 默认排序、主动排序方向和稳定次级排序如何定义；
5. 未来四类媒体在尚无类型 Requirement 时，卡片显示哪些中性公共字段；
6. 是否采用渐进加载，以及当前宿主支持的安全实现方式；
7. 现有 媒体库单个视图.xdb、两个卡片插件和历史脚本哪些必须保持哈希不变；
8. 如何在不复制卡片业务逻辑的前提下实现集合通用卡；
9. 自动测试、validator 和真实人工验收分别覆盖什么。
